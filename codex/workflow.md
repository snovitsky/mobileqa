# Порядок работы

Текущая передача от 2026-10-19 отдельно согласована владельцем: все подготовленные изменения доставить прямо в main, без создания staging и без включения магазина. Целевой порядок ниже действует после первоначальной настройки следующей командой. Вход для другого разработчика/Codex — раздел передачи в store-release-plan.md. Store automation дополнительно заблокирована отслеживаемым automationEnabled=false.

Владелец подтвердил staging (разработка) → main (магазинный выпуск). Обе ветки проходят одинаковый полный CI: тесты, поиск секретов, обычную/store сборки и аудит пакета. Различается только доступ к публикации после проверок. Локальная автоматизация подготовлена, удалённая настройка ещё не выполнена. Первое создание staging и доставка требуют commit/release pre-flight. Процесс — [store-release-plan.md](store-release-plan.md).
1. Прочитать AGENTS.md, этот документ и индекс контекста, проверить git status. Разрабатывать в собственном клоне в staging; перед задачей получать актуальную целевую ветку через git pull --ff-only, сохраняя незакоммиченные файлы без резервных копий. main используется для согласованного выпуска.
2. Проследить затронутый поток по конкретным файлам. Перед кодовыми изменениями кратко сообщить план, риски и проверки по-русски. Действовать в уже разрешённой области задачи.
3. Внести минимальные поддерживаемые изменения; не устанавливать зависимости ради документации.
4. Выполнить релевантные проверки из [checks.md](checks.md); явно отделить исполненные команды от предложенных сценариев. Перед push обязательно npm test и npm run build на Node 22+ с установленными зависимостями и Chromium. Отсутствие обязательных remote checks не отменяет локальные проверки.
5. Перед финальным ответом решить, изменились ли знания о поведении, процессах, контрактах, данных, рисках или проверках. Если да, обновить `codex/changelog.md` и затронутые профили. Если нет, объяснить причину; при незавершённости перечислить остаток.
6. В финальном ответе выбрать один статус:

Документация codex/: обновлена / не требовалась / осталась незакрытой

## Коммит и доставка

Коммит требует отдельного pre-flight и явного подтверждения: git status, точные файлы, резюме, сообщение `type: описание` на русском и результаты проверок. Посторонние изменения перечислять отдельно. Сам факт редактирования файлов не разрешает коммит/push.

Запрос на полную доставку требует определения цели: ZIP через npm run build/Actions либо загрузка unpacked extension; см. [deploy.md](deploy.md). Не придумывать серверный deploy или публикацию в магазине. Для согласованной цепочки проверок/commit/push/публикации показать один объединённый pre-flight с веткой, целью и оставшимися действиями; подтверждение не повторять при неизменной области. Push разработки в staging; после полного успешного CI продвигать согласованный SHA в main и проверять такой же полный CI. Без force; обязательные PR не вводить автоматически. Если upstream изменился, получить изменения и согласовать конфликты. Сетевые HTTPS Git-команды на Windows — сразу через require_escalated, локальные — в обычной среде.

Каждая задача начинается с Issue: проблема, ожидаемый результат, способ проверки, исполнитель и затрагиваемые модули. Один Issue — один основной исполнитель; пересечения файлов согласовать до работы. Не использовать общую рабочую папку двух исполнителей и не менять одни файлы одновременно. Не отправлять сообщения/создавать Issue от имени пользователя без разрешения. Если разрешения на внешнюю запись нет, подготовить описание задачи локально. Изменения протокола/permissions/форм требуют причины и регрессионного теста; permissions не расширять без явной инструкции. Контракт — в [api-map.md](api-map.md).

Делать небольшие понятные коммиты с описанием результата; проверку коллегой можно выполнять по коммитам. Крупный рефакторинг сначала выполнять отдельно, затем распределять задачи по модулям; не смешивать перемещение кода и новую функциональность. По ранее зафиксированному соглашению обязательные PR не вводятся автоматически. Для staging и main обязательны полные проверки; продвижение main выполняется после успешного staging CI. Force push и удаление main запрещены. Состояние branch protection в аккаунте пока независимо не подтверждено.

## Подготовка среды и ручная проверка

Node.js 22+, `npm ci`, `npx playwright install chromium`; на Linux для системных зависимостей `npx playwright install --with-deps chromium`. Затем `npm test` и `npm run build`. Тесты используют локальные fixture и отдельные временные Chromium profiles. Рабочие сайты и клиентские формы не использовать для автоматических отправок.

В chrome://extensions загрузить папку extension/ в developer mode. После правок нажать «Обновить» на карточке расширения и открыть панель заново. Пользовательские сценарии — в [user-guide.md](user-guide.md), проверки — в [checks.md](checks.md), выпуск — в [deploy.md](deploy.md).

Секреты не записывать. Дополнительные резервные копии и архивы истории не создавать. Changelog при росте более 800 строк проверить на сжатие; более 1200 — сжатие рекомендовано, более 2000 — обязательно, без отдельного архива.

## Заметки production и доступ к публикации

Перед продвижением Codex сверяет фактическую Store-версию и prod/vVERSION SHA, объединяет итоговые изменения разработки в один понятный пользователю список, обновляет extension/release-notes.json и заранее готовит releases/VERSION.md командой npm run notes:write. CI валидирует текст/базу/пакет, но не заменяет содержательную проверку текста. Промежуточные номера разработки не становятся отдельными опубликованными записями. Невыпущенную запись можно уточнять, опубликованные записи не переписывать.

Google OIDC разрешён только main jobs Store workflows. CWS_PUBLISH_ENABLED должен быть repository variable; пока конфигурация/карточка/первый production не проверены — false. Создание коммита, push обеих веток и включение фактической публикации требуют конкретного согласованного pre-flight. Все данные доступа других проектов запрещены; сигнатурный scanner не доказывает отсутствие секрета неизвестного формата.
