# Порядок работы

1. Прочитать AGENTS.md, этот документ и индекс контекста, проверить git status. Работать в собственном клоне только в main; перед задачей получать актуальный main через `git pull --ff-only`, сохраняя незакоммиченные файлы без резервных копий. Не создавать отдельные ветки.
2. Проследить затронутый поток по конкретным файлам. Перед кодовыми изменениями кратко сообщить план, риски и проверки по-русски. Действовать в уже разрешённой области задачи.
3. Внести минимальные поддерживаемые изменения; не устанавливать зависимости ради документации.
4. Выполнить релевантные проверки из [checks.md](checks.md); явно отделить исполненные команды от предложенных сценариев. Перед push обязательно npm test и npm run build на Node 22+ с установленными зависимостями и Chromium. Отсутствие обязательных remote checks не отменяет локальные проверки.
5. Перед финальным ответом решить, изменились ли знания о поведении, процессах, контрактах, данных, рисках или проверках. Если да, обновить `codex/changelog.md` и затронутые профили. Если нет, объяснить причину; при незавершённости перечислить остаток.
6. В финальном ответе выбрать один статус:

Документация codex/: обновлена / не требовалась / осталась незакрытой

## Коммит и доставка

Коммит требует отдельного pre-flight и явного подтверждения: git status, точные файлы, резюме, сообщение `type: описание` на русском и результаты проверок. Посторонние изменения перечислять отдельно. Сам факт редактирования файлов не разрешает коммит/push.

Запрос на полную доставку требует определения цели: ZIP через npm run build/Actions либо загрузка unpacked extension; см. [deploy.md](deploy.md). Не придумывать серверный deploy или публикацию в магазине. Для согласованной цепочки проверок/commit/push/публикации показать один объединённый pre-flight с веткой, целью и оставшимися действиями; подтверждение не повторять при неизменной области. Push напрямую в main, без force; отдельные ветки и обязательные PR не использовать. Если upstream изменился, получить изменения и согласовать конфликты. Сетевые HTTPS Git-команды на Windows — сразу через require_escalated, локальные — в обычной среде.

Каждая задача начинается с Issue: проблема, ожидаемый результат, способ проверки, исполнитель и затрагиваемые модули. Один Issue — один основной исполнитель; пересечения файлов согласовать до работы. Не использовать общую рабочую папку двух исполнителей и не менять одни файлы одновременно. Не отправлять сообщения/создавать Issue от имени пользователя без разрешения. Если разрешения на внешнюю запись нет, подготовить описание задачи локально. Изменения протокола/permissions/форм требуют причины и регрессионного теста; permissions не расширять без явной инструкции. Контракт — в [api-map.md](api-map.md).

Делать небольшие понятные коммиты с описанием результата; проверку коллегой можно выполнять по коммитам. Крупный рефакторинг сначала выполнять отдельно, затем распределять задачи по модулям; не смешивать перемещение кода и новую функциональность. По ранее зафиксированному соглашению владельца обязательные PR/review/remote checks отключены, прямой push допустим, force push и удаление main запрещены. Это описание соглашения, не независимая проверка настроек GitHub; CI продолжает запускаться после push в main.

## Подготовка среды и ручная проверка

Node.js 22+, `npm ci`, `npx playwright install chromium`; на Linux для системных зависимостей `npx playwright install --with-deps chromium`. Затем `npm test` и `npm run build`. Тесты используют локальные fixture и отдельные временные Chromium profiles. Рабочие сайты и клиентские формы не использовать для автоматических отправок.

В chrome://extensions загрузить папку extension/ в developer mode. После правок нажать «Обновить» на карточке расширения и открыть панель заново. Пользовательские сценарии — в [user-guide.md](user-guide.md), проверки — в [checks.md](checks.md), выпуск — в [deploy.md](deploy.md).

Секреты не записывать. Дополнительные резервные копии и архивы истории не создавать. Changelog при росте более 800 строк проверить на сжатие; более 1200 — сжатие рекомендовано, более 2000 — обязательно, без отдельного архива.
