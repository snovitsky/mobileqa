# План автоматического выпуска в Chrome Web Store

## Передача следующему разработчику и Codex — начать отсюда

Решение владельца от 19 октября 2026: **сейчас передать все подготовленные правки и договорённости в main; назначение исполнителя и подключение магазина отложены**. Не создавать staging и не входить в аккаунты вместо владельца в рамках этой передачи. Владелец отдельно выберет, кто настраивает публикацию. Ни готовый код, ни эта инструкция сами по себе не разрешают включить публикацию.

### Цель и неизменные договорённости

- Расширение публикуется как **Unlisted — установка по ссылке**. Ссылку может использовать любой её получатель; это не список разрешённых сотрудников. Издатель Brandmaker, поддержка info@brandmaker.ru.
- Будущая разработка — `staging`, production — `main`; отдельная `main-prod` не нужна. Обе ветки проходят **один и тот же полный CI**, включая все тесты, поиск секретов, обычную и магазинную сборки, проверку состава и release provenance. У staging нет publisher credentials.
- После согласованного продвижения в main и успешного CI следующий выпуск отправляется автоматически. Ручных загрузок очередных версий не должно быть. Первоначальное создание карточки/фиксация Unlisted может потребовать одного ручного этапа.
- Пользовательские патчноуты — один итоговый список от **фактически опубликованной** версии до кандидата. Пример: Store 2.6.20 → кандидат 2.7.1, без отдельных публичных разделов промежуточных dev-версий. База подтверждается Store status + production tag/source SHA, а не вершиной main.
- Обновления доставляет Chrome. Приложение сообщает о реально подготовленной Chrome версии, показывает изменения и применяет её после подтверждённого завершения QA-сеанса. Никакого скачивания исполняемого кода с GitHub.
- Не использовать доступы Метрики или других проектов. Chrome permissions не расширять без явной инструкции. Не хранить токены, приватные ключи, .env или клиентские данные в репозитории/ZIP/логах.

### Порядок продолжения

1. Получить актуальный main и прочитать AGENTS.md → codex/README.md → этот документ → store/setup.md → store/listing.md → codex/store-security-review.md. Проверить рабочее дерево, существующие ветки, Actions и отсутствие незавершённого Store-кандидата. Не делать выводов по истории чата другого разработчика.
2. С владельцем определить ответственного, аккаунт издателя, отдельный/существующий Google Cloud project и право выполнить первую публикацию. Самому не искать доступы других проектов. Пароли/JSON-ключи в чат не запрашивать.
3. Создать staging от согласованного main после проверки, что она ещё не существует. Разрабатывать там; main использовать для подготовленного выпуска. Проверить реальные полные CI обеих веток; их тестовые шаги не сокращать. Не использовать force push или удаление веток для обхода расхождений.
4. Проверить установленный lockfile/Chromium, выполнить npm test, npm run build, npm run build:store. Проверить состав ZIP и `npm run audit:secrets`. Взять пакет из успешного CI, сохранить его SHA/run ID/digest. Локальные demo assets при необходимости заново получить через npm run store:assets; они не находятся в runtime ZIP.
5. Создать карточку существующего издателя с этим store ZIP, записать реальные itemId/publisherId, заполнить описание/поддержку/политику и изображения. Публичные ссылки после доставки main: `https://github.com/snovitsky/mobileqa/blob/main/store/privacy.md` и `https://github.com/snovitsky/mobileqa/blob/main/releases/2.6.20.md`. Проверить их без входа. Если репозиторий станет private, заменить публичным разделом сайта Brandmaker.
6. Настроить Google service account и WIF без постоянного ключа. Scope доверия: конкретный repository_id, ref main и environment chrome-web-store. Публикующему аккаунту не нужны Cloud Owner/Editor. Привязка к издателю, ограничения и список variables подробно перечислены в store/setup.md. `CWS_PUBLISH_ENABLED` — именно repository variable, остальные могут быть environment variables.
7. Выполнить `Chrome Web Store review status` вручную с `verify_connection=true`. Это отдельный job с contents:read и CWS readonly scope, он работает до активации публикации и не запускает monitor/создание production-тега. Сопоставить ID/status с Dashboard.
8. Завершить первый выпуск/Unlisted по инструкции setup. Если он отправлен вручную, использовать **точный ZIP успешного main CI**, дождаться PUBLISHED нужной версии и выполнить `Record first Chrome Web Store publication` с CI run ID и явным подтверждением пакета. Bootstrap ничего не загружает в Store. API не сообщает hash уже опубликованного ZIP: эта первая связь явно помечается как подтверждение оператора. Не выдавать её за независимо доказанный API hash.
9. После согласования и готовности аккаунта изменить `store/release-state.json` на automationEnabled=true, включить repository variable CWS_PUBLISH_ENABLED=true и показать новый commit/release pre-flight. До этого оставить оба блокиратора выключенными. Первое значение хранится в Git, второе — в GitHub settings; одного переключателя недостаточно.
10. При следующем выпуске прочитать Store published version и prod/vVERSION source SHA; подготовить понятные пользователям итоговые changes в extension/release-notes.json, выполнить npm run notes:write. Обновить версии согласованно. Провести полный staging CI, согласованное продвижение main, такой же полный main CI. Publish должен отправить именно проверенный artifact; monitor завершает release только после фактического Store PUBLISHED 100%.
11. Установить/обновить реальную магазинную копию, проверить показ версии, ссылку на изменения, «Позже»/кнопку из настроек, подтверждение завершения сеанса и сохранение обычных настроек. Unpacked-копия с другим ID не доказывает работу магазинной доставки.

### Ограничения, которые нельзя потерять при передаче

Отказ модерации, конфликт базы/тегов/digest, другой pending-кандидат, warning/takedown или неизвестный ответ на upload/publish требуют сверки, а не слепого повторения. Async upload без подтверждённой точной версии останавливается для ручного разбора. Успешный Actions upload не означает Store PUBLISHED. Откат — новый выпуск с большим номером из рабочего исходного состояния, не уменьшение version. Полный локальный PASS не заменяет Ubuntu CI и настоящее обновление Chrome. Известная прежняя нестабильность focus regression отражена в checks.md; не считать её устранённой одной повторной попыткой. Поиск секретов сигнатурный, без гарантии распознавания любого неизвестного формата; Git history/другие проекты не сканировались.

## 1. Выбранная схема веток

Используем `staging` для разработки и `main` для выпуска. Существующий main остаётся основной веткой и будущей точкой запуска production workflow; переименовывать его или вводить main-prod не требуется.

После первоначальной настройки разработчик накапливает изменения в staging. Когда нужен выпуск, Codex сверяет их с последней действительно опубликованной версией, готовит единый пользовательский список изменений, обновляет версии, выполняет проверки и показывает commit/release pre-flight. После явного подтверждения выполняется продвижение подготовленного состояния в main без force push. Только после отдельной активации обоих блокираторов push в main означает автоматическую отправку этого выпуска в магазин. Дополнительного ручного нажатия «Опубликовать» после каждого push не планируется. Текущая передача кода в main выполняется без такой активации.

После перехода нужно одновременно обновить AGENTS.md и workflow.md: разработка в staging, выпуск через main, подтверждение pre-flight остаётся обязательным. Новый main нельзя использовать для обычных экспериментальных коммитов. Защитить main от удаления/force push; право продвижения оставить согласованным исполнителям. Обязательные PR не вводить автоматически: это отдельное решение владельца. Если понадобятся PR, использовать staging → main для выпуска, без второго несогласованного процесса.

Важно: вершина main — кандидат на выпуск. Пока Google проверяет его, фактическая production-версия остаётся предыдущей.

## 2. Однократная подготовка магазина

1. В аккаунте издателя проверить двухфакторную аутентификацию, контакт поддержки и сведения издателя. Условия и подтверждения аккаунта принимает владелец аккаунта.
2. Создать карточку Brandmaker QA с магазинным ZIP, где manifest.json находится в корне. Сохранить постоянные publisherId и itemId. Следующие версии обновляют эту же карточку и сохраняют ID расширения.
3. Подготовить описание назначения, скриншоты, значок и рекламное изображение требуемого формата. Не обещать аппаратную эмуляцию телефона или гарантированное обнаружение всех дефектов вёрстки.
4. Опубликовать доступную без входа политику конфиденциальности, указать её URL и честно заполнить раздел Privacy practices. Локальная обработка адресов, взаимодействий и отчётов также описывается; нельзя заменять это обещанием «никакие данные не используются».
5. Выбрать **Unlisted — доступ по ссылке** и нужные регионы. Любой получивший ссылку сможет установить расширение; это не ограничение по конкретным сотрудникам. Для ограничения списка пользователей нужен Private, что отличается от выбранной задачи. Любая видимость проходит проверку магазина и соблюдает одинаковые политики.
6. Завершить первоначальную настройку/публикацию выбранной видимости в dashboard. API работает с существующей карточкой и её сохранёнными настройками. Этот одноразовый этап не означает ручные загрузки последующих обновлений.

Источники: [видимость](https://developer.chrome.com/docs/webstore/cws-dashboard-distribution), [первая публикация](https://developer.chrome.com/docs/webstore/publish), [подготовка пакета](https://developer.chrome.com/docs/webstore/prepare), [изображения](https://developer.chrome.com/docs/webstore/images), [Privacy practices](https://developer.chrome.com/docs/webstore/cws-dashboard-privacy). Итоговые поля аккаунта и требования к конкретной карточке проверяются при настройке; доступа к аккаунту в этой задаче не было.

## 3. GitHub Actions и доступ к магазину

Предпочтительно использовать GitHub OIDC → Google Workload Identity Federation → отдельный Google service account → Chrome Web Store API v2. Постоянный JSON-ключ аккаунта и пользовательский refresh token в репозитории не нужны. Включить API, привязать service account к издателю в dashboard. У одного издателя поддерживается один такой service account, поэтому заранее проверить существующую привязку.

WIF доверяет конкретному repository_id и production-ветке main, с дополнительным ограничением environment при его использовании. Право impersonation выдаётся только этой GitHub identity; service account не получает Owner/Editor всего Google Cloud. Учитывать, что привязка CWS даёт возможности на уровне издателя, а не только одного выбранного item.

В конфигурации GitHub хранить publisher/item ID, номер проекта, имя WIF provider и email service account. Это идентификаторы, не приватные ключи. `id-token: write` включается только в deploy job; обычные тесты имеют `contents: read` и не могут публиковать. Actions закреплять на проверенные SHA, npm устанавливать по lockfile. Не выводить access token/Authorization в логи; по возможности не создавать файл credentials на runner.

Источники: [service accounts](https://developer.chrome.com/docs/webstore/service-accounts), [Google auth Action](https://github.com/google-github-actions/auth), [GitHub OIDC в Google Cloud](https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-in-google-cloud-platform).

## 4. Список изменений между production-выпусками

Пример: в магазине реально опубликована 2.6.20, в staging накопилась 2.7.1. Публичный выпуск 2.7.1 содержит **один список итоговых изменений от 2.6.20 до 2.7.1**. Промежуточные номера разработки не превращаются в отдельные публичные разделы.

Перед продвижением Codex обязан:

1. Прочитать фактическую опубликованную версию через fetchStatus магазина и сопоставить её с сохранёнными данными успешной поставки: source SHA, ZIP SHA-256 и production tag `prod/v<version>`.
2. При несовпадении/неизвестной базе остановить подготовку выпуска для сверки. Нельзя брать за базу предыдущий коммит main, последний dev-тег или последний случайный GitHub Release.
3. Сравнить исходники и поведение от baseline SHA до кандидата. Сгруппировать пользовательские улучшения, объединить повторения, убрать внутренние исправления ошибок, которые появились и исчезли только в staging. Не включать невыпущенные обещания.
4. Подготовить `releases/<target-version>.md` и структурированные данные для встроенной страницы. Метаданные: targetVersion, fromVersion, baseline SHA, дата и заголовок. У первого магазинного выпуска fromVersion=null: опубликованной базы ещё нет.
5. Написать текст обычным языком: что стало удобнее, что исправлено, требуется ли действие пользователя. Без имён функций, селекторов и простого копирования git log. Пример: «Подсказки в адресной строке помогают выбрать сайт, к которому уже разрешён доступ».
6. Показать этот список вместе с release pre-flight. CI проверяет наличие, структуру, версии и соответствие базы магазину; смысловую полноту текста проверяет Codex/человек. Не обещать, что обычный CI сам достоверно сочинит все изменения.

extension/release-notes.json переведён на production-записи: первый кандидат 2.6.20 имеет fromVersion=null и baselineSha=null, промежуточная dev-запись 2.6.19 удалена. releases/2.6.20.md подготовлен заранее и проверяется на точное совпадение. Это ещё не подтверждение публикации.

Заметки должны быть доступны по постоянной ссылке уже до отправки кандидата в магазин: например, публичный versioned-файл releases в этом репозитории после push. После установки та же запись читается из пакета без интернета. Если репозиторий станет закрытым, нужен публичный раздел сайта Brandmaker. Общий указатель «последний production» обновляется только после подтверждённой публикации. Утверждённые записи не переписывать как заметки другого релиза.

## 5. Автоматическая цепочка после push в main

1. Checkout точного SHA, установка Node/Chromium и зависимостей по lockfile.
2. Полный `npm test`, затем обычная сборка и `npm run build:store`. Любая ошибка завершает цепочку до получения токена магазина. Нельзя автоматически повторять упавшие тесты до случайного зелёного результата.
3. Проверка магазинного ZIP: только явный runtime allowlist, корневой manifest, согласованные версии/permissions, локальные исполняемые файлы, отсутствие внутренних документов/тестов/секретов. Smoke-тест загружает именно распакованный результат этого ZIP.
4. Сохранение ZIP и отчётов с привязкой к SHA; вычисление SHA-256. Deploy получает тот же artifact, не пересобирает иной пакет.
5. Получение краткоживущего OIDC-токена и fetchStatus. Проверить item/publisher, доступность карточки, published version, отсутствие другого кандидата на модерации, соответствие fromVersion и возрастание номера.
6. Upload пакета в существующий item. Дождаться успешного состояния загрузки, проверить возвращённый номер версии; обрабатывать IN_PROGRESS, SUCCEEDED, FAILED по текущей API-схеме.
7. Вызвать publish с `publishType: DEFAULT_PUBLISH`, `skipReview: false`, `blockOnWarnings: true`. Это запрос модерации с автоматическим выпуском после одобрения. Предупреждения требуют разбора, а не автоматического обхода.
8. Записать состояние SUBMITTED/PENDING_REVIEW. Успех upload/publish-запроса ещё не является успехом публикации для пользователей.
9. Отдельный workflow мониторинга регулярно сверяет статус незавершённой поставки. Не держать один runner несколько дней. Предусмотреть ручной повтор чтения статуса без повторного upload. При REJECTED/TAKEN_DOWN/неожиданной версии — явная ошибка и причина; автоматической отмены чужого кандидата нет.
10. Только когда published distribution действительно содержит ожидаемую версию, отметить deployment successful, создать неизменяемый production tag для source SHA и GitHub Release с единым пользовательским списком изменений и контрольными суммами.

Concurrency публикации не отменяет идущий deploy новым push. Пока Google рассматривает выпуск, следующий production-кандидат блокируется, разработка в staging продолжается. Таймаут ответа после upload/publish требует сначала сверки состояния через API: слепой повтор операции может создать неоднозначность.

Данные поставки: версия, previous production version, source SHA, ZIP SHA-256, hash заметок, item ID, время отправки и публикации. Это release assets/deployment metadata вне магазинного ZIP. Не коммитить эти данные обратно в main так, чтобы запускалась рекурсивная публикация. Документационные коммиты без изменения пакета могут пропускать upload только после явного сравнения версии/пакета; изменение runtime без увеличения версии должно завершаться ошибкой.

API: [upload](https://developer.chrome.com/docs/webstore/api/reference/rest/v2/media/upload), [publish](https://developer.chrome.com/docs/webstore/api/reference/rest/v2/publishers.items/publish), [fetchStatus](https://developer.chrome.com/docs/webstore/api/reference/rest/v2/publishers.items/fetchStatus). Срок модерации не контролируется GitHub: [процесс рассмотрения](https://developer.chrome.com/docs/webstore/review-process).

## 6. Что увидит пользователь

Обновления распространяет Chrome через магазин, не GitHub и не скачиваемый расширением исполняемый код. Открытая панель может задерживать установку. Нельзя обещать, что все пользователи получат новую версию сразу после зелёного Actions.

В локальном кандидате реализованы отдельные состояния:

- Chrome сообщил `runtime.onUpdateAvailable`: «Доступна версия X» со ссылкой «Что изменилось», кнопками «Обновить» и «Позже». Это готовое к установке обновление; наличие нового коммита в staging не повод для такого сообщения.
- «Обновить»: по явному нажатию завершить активный QA-сеанс, убрать его временные правила/очереди, сохранить обычные настройки и выполнить `chrome.runtime.reload()`. Объяснить завершение сеанса перед действием. Не сохранять содержимое форм, пароли или обещать восстановление состояния чужого сайта.
- После `onInstalled` reason=update: «Обновлено до X», ссылка на встроенный список изменений. Это уже установленная версия, а не предложение обновиться ещё раз.
- «Позже» оставляет рабочую панель доступной. Информационное обновление не меняет цвет индикатора состояния QA-сеанса на ошибку.

Не делать unconditional requestUpdateCheck на каждом открытии или таймере: использовать события Chrome. onUpdateAvailable сохраняет готовую версию; панель показывает обновление и настройки позволяют вернуться к нему после «Позже». Подтверждённое применение получает сохранение/остановку от всех открытых панелей, затем удаляет временные правила/регистрации/сессии и вызывает runtime.reload. Ошибка сохранения/очистки блокирует reload. Unit и browser-fixtures не заменяют проверку настоящего обновления из магазина.

Источники: [жизненный цикл обновления](https://developer.chrome.com/docs/extensions/develop/concepts/extensions-update-lifecycle), [runtime API](https://developer.chrome.com/docs/extensions/reference/api/runtime).

Первый переход с unpacked-версии потребует установки магазинной версии по ссылке. У неё может отличаться ID, и настройки старой установки автоматически не переносятся. Старую тестовую копию желательно отключить, чтобы не открывать две разные панели.

## 7. Сбои и возврат к рабочему поведению

Магазин не следует считать каналом мгновенного отката: для исправления публикуется версия с большим номером, при необходимости из последнего рабочего исходного состояния. Номер назад не уменьшаем; автоматическое удаление карточки не откатывает уже установленные копии. Каждая такая поставка снова проходит проверки и процедуру магазина. Сохраняются штатные release artifacts, дополнительные backup-архивы не создаются.

При ошибке тестов/сборки ничего в магазин не отправляется. При ошибке авторизации исправляется WIF/привязка. При отказе модерации исправляется причина и готовится следующий кандидат. При успехе публикации, но ещё старой версии у пользователя, проверяются магазинный ID, Chrome update lifecycle, открытые панели и ограничения администратора браузера.

## 8. Порядок внедрения и приёмка

1. Завершить локальную подготовку пакета, аудит и пользовательские исправления; устранить воспроизводимость нестабильного focus-теста в Ubuntu перед полностью автоматическим выпуском.
2. Создать карточку, утвердить описание/приватность/Unlisted, подготовить графику и выполнить однократную настройку первого выпуска.
3. Настроить WIF и service account. Проверить read-only fetchStatus; не публиковать тестом неподтверждённый production-пакет.
4. Создать staging из согласованного актуального main, изменить инструкции и CI-триггеры. Для staging — проверки без права публикации.
5. Внедрить production notes, publish и monitor workflows, provenance и защиту от параллельных кандидатов.
6. Реализовать onUpdateAvailable и безопасное применение обновления; протестировать оба состояния уведомления и сохранение настроек.
7. Провести первый согласованный автоматический выпуск: точный ZIP из проверенного SHA, подтверждённая модерация, обновление установленной из магазина копии, совпадение заметок в панели и на публичной странице.

Обязательные отрицательные проверки: staging/PR не получают право публикации; отсутствующие notes, неверная база, меньшая версия, лишний файл ZIP, секретная сигнатура, упавший тест и pending-кандидат блокируют upload; отклонение модерации не обозначается как published; повторное чтение статуса не загружает пакет заново. Отдельно проверить первый выпуск без baseline и следующий агрегированный выпуск через несколько dev-версий.

Готовность означает работающую цепочку от согласованного продвижения staging до реально опубликованной версии и обновлённого пользовательского экземпляра. Один зелёный build этого не подтверждает.

## Реализованные workflow и первая ручная публикация

CI один и тот же для main и staging: полный npm test (включая поиск секретов), обычная/store сборки и provenance. Ни один обязательный шаг не пропускается в staging. store-publish.yml запускается только от успешного push-CI main текущего репозитория и получает artifact точного SHA/run ID; CWS_SOURCE_SHA отделён от SHA самого workflow_run. Публикация выключена, пока repository variable CWS_PUBLISH_ENABLED не равна true.

store-status.yml читает незавершённый draft-кандидат дважды в час, использует readonly CWS scope и не повторяет upload/publish. Ручной verify_connection проверяет связку даже до первой отправки. Draft и release assets сохраняют пакет/заметки/метаданные; prod/vVERSION создаётся только после Store PUBLISHED 100%. docs-only повтор с неизменными байтами пакета/заметок пропускает загрузку.

Если первая фиксация Unlisted потребует ручной публикации, загрузить точный ZIP успешного CI с выключенной автоматикой. После одобрения запустить store-bootstrap.yml с ID этого CI run и явным подтверждением точного файла. Этот workflow не загружает и не публикует в CWS, только читает статус и фиксирует GitHub provenance. Поскольку API не возвращает hash опубликованного ZIP, первоначальная связь байтов опирается на подтверждение оператора и явно так маркируется. Затем включить автоматизацию для следующих версий. Подробности — ../store/setup.md.
